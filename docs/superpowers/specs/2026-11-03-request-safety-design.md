# 请求防重复与外部挂单核对

用户确认先补两项：持久化开单请求去重/查询，以及同币种外部入场挂单核对；沿用当前仓库、原生Freqtrade和既有提交推送部署流程。本轮不增加风险预算、总览或交易信号。

## 请求语义

- 同一TG消息（chat_id/message_id）稳定映射为请求编号；同一编号重放只返回原结果，参数变化拒绝。新消息即新请求，主动加仓继续通过既有仓位/挂单/止损校验。
- 请求日志使用user_data内独立SQLite，主键唯一、持久提交；保留规范化参数、状态、时间、结果和关联订单。沿用交易线程串行执行，不改原生数据库表。
- 原生RPC调用前持久标记submitting。之前失败为rejected；之后任何未确认异常为unknown，保留计划，禁止同币种新入场，不自动重发。成功为submitted。
- 原生enter_tag/ft_order_tag附加请求编号，兼容每笔TTL。重启或查询时用原生持久订单恢复关联；找不到记录不能推断交易所未接单。检查阶段中断可安全拒绝，但绝不自动重放原请求。
- /request [编号] 查询一条或最近5条。未知请求可在用户核对后以 /request <编号> resolve 显式解除；命令仍须实时仓位一致且无潜在入场挂单，不重新提交旧请求。旧编号始终不再下单。
- 只覆盖新版本TG开仓/加仓消息，不追溯旧请求；止盈、止损、平仓、撤单不受请求日志阻塞。请求存储故障时新入场失败关闭，禁止无日志提交。

## 外部挂单

- 实盘新开仓/加仓在计划修改及RPC之前，同时刷新该币种普通挂单和条件挂单；Binance适配使用已安装CCXT的fetch_open_orders，trigger=True读取条件单。
- 只减仓或整仓关闭标志明确、类型一致的退出单可以保留；潜在增加敞口的订单、标志矛盾/缺失、无法确认的状态/模式以及查询失败都阻止新增入场。不同币种不阻塞。
- 不因buy/sell方向推断只平仓，不忽略条件入场单；不自动撤销外部订单。退出流程不增加此校验。核对与提交间其他客户端仍可能改变账户，无法保证跨客户端原子性。

## 方案与边界

采用独立SQLite请求日志+原生订单标签关联，复用官方下单。仅内存锁不能跨重启去重；改造原生clientOrderId传递会扩大框架适配面。本轮选择前者：交易所接单但本地尚未持久化时，保守保留unknown并等待核实，不能承诺跨交易所/本地原子提交或自动恢复所有未知结果。

用离线真实SQLite及原生订单集成测试覆盖重复、重启、不同新消息、未知状态、手动解除、落盘失败、标签TTL兼容、普通/条件/只减仓/畸形回执和退出不受影响。完整回归及一次独立审查后，备份记录并更新服务；不提交实盘测试单或人为注入线上故障。
