# 执行可靠性：独立守护与开仓前仓位核对

状态：用户已同意先做这两项，并选择当前主机的独立守护容器；具体规则已获用户确认，继续实施。

## 方案和范围

选择同机独立容器：能在交易进程卡住、停止或无法连接交易所时独立检查并通知 TG。另一台机器可额外发现整机离线，但需要额外环境，用户未选择。复用官方 Freqtrade 2026.10 和现有 Compose，不修改框架核心，不启用 HTTP API，不挂载 Docker socket。

本次只增加独立守护，以及 TG 开仓/加仓前的真实仓位校验。挂单有效期、风险预算和新的止损确认功能留到后续，不改变现有退出逻辑。

## 独立守护

- 交易进程在独立状态文件中发布原生 `last_process`（最后完成交易循环的时间）、运行状态和快照时间。使用轻量后台发布线程，只读原生字段，不访问交易 ORM，不把“线程还活着”当作交易循环正常。
- 守护容器默认每 30 秒检查。首次启动宽限 180 秒；`RUNNING`/`PAUSED` 时循环完成时间超过 180 秒、快照过期或状态文件缺失/无效均为异常。重复重启交易进程不得无限延长宽限。
- 手动 `/stop` 通知一次“交易处理已停止”；`/pause` 仍管理已有仓位，只要循环正常就不报掉线。进程退出/卡住由过期状态识别。
- 独立检查 Binance 现货元数据和 USDT 合约公共接口连通性，连续两次失败才告警。公共连通检查不代表交易权限验证，真实账户可用性仍由下单前校验确定。
- 状态变化时通知：异常通知一次，恢复通知一次；保持异常不刷屏。通知状态单独持久保存。TG 不可达时保留待通知信息，恢复后合并为一条摘要，不批量补发旧消息；通知采用尽力送达语义。守护记录无法读取或写入时，以内存继续监测并明确通知降级，存储恢复后补存状态；降级期间重启可能重复通知，不因记录损坏重新获得宽限。
- 守护只得到 TG token/chat_id（配置了 topic 时也沿用）与只读健康文件，不读取交易所 key/secret、持仓计划或交易数据库。不输出 token、签名 URL 或原始认证异常。
- 守护不自动重启机器人，不取消订单，不开仓、加仓或平仓。整机断电或整机断网时，同机守护不能及时发出 TG 通知。

## TG 开仓/加仓前核对

- 对 `/forcelong`、`/forceshort` 的每次实盘请求，使用官方 `fetch_positions(pair)` 新鲜查询该交易对真实仓位，在修改计划、提交订单之前完成核对。模拟模式不查询真实账户。
- 本地没有该币种持仓、交易所却有非零仓位：拒绝开仓并明确提示“存在未接管仓位”。不自动接管，不靠反向开仓抵消。
- 加仓时方向和实际数量必须与本地持仓一致，合约数量按 contractSize 换算为基础币数量；仅容忍浮点误差，不能忽略一个交易步长的差异。多个方向、缺失/异常字段或本地记录异常均拒绝。
- 交易所数量为零但本地仍有已成交持仓，或交易所查询失败/超时：拒绝开仓/加仓，不把查询失败当成空仓。保留原有计划和记录，提示先核对 `/status`、`/order` 与交易所。
- 不同币种的外部仓位不会阻止该交易对的正常请求；助手已有挂单继续沿用现有“存在未完成订单则不能加仓”的限制。此功能不扫描、接管或撤销外部挂单。
- 只限制增加风险的开仓/加仓；止损、止盈、部分退出与 `/forceexit` 不受此校验阻塞。不自动修改真实仓位或本地账本。外部手工交易与查询之间仍可能竞态，核对不构成交易所侧的原子锁。

## 实施和验证

使用独立工作区开发，先写离线回归测试。覆盖循环卡住而发布线程仍运行、启动缺失、停止/暂停、故障去重/恢复/TG 失败重试，以及空仓、外部仓位、方向/数量不符、合约面值、查询失败与模拟模式。回归现有交易、监控和 TG 测试，并做一次独立代码审查。

沿用本会话已授权的提交、推送和启动流程。上线前核对并备份当前助手交易数据库和计划，保留真实挂单与持仓；不提交测试订单。核验新容器运行、有效心跳、原有交易/计划保持，以及守护启动正常。
