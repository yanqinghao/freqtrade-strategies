# Telegram 开单助手

基于官方 Freqtrade **2026.10**，只保留手动开仓、加仓、分批止盈、保护止损和平仓。交易核心与 RPC 使用官方实现，`telegram.py` 是一层精简扩展，不再维护整个框架的副本。

## 交易指令

```text
/forcelong BTC 100 3 sl=90000 price=95000 tp=98000,100000,105000
/forcelong BTC 100 3 sl=90000 price=95000 ttl=1h
/forceshort BTC 100 3 sl=105000 tp=98000,95000,90000
/setmanual 1 sl=96000 tp=98000,100000,105000
/close 1 50
/forceexit 1
/coo 1
/manual
/status table
```

以上价格仅演示格式。币种后两项分别为**本次保证金 USDT**与杠杆；`price` 省略时使用市价。新开仓必须提供 `sl`，止盈可选，最多三档。完整交易对如 `BTC/USDT:USDT` 也可使用。开仓币种不限于监控的三币种，以交易所支持为准。

新限价开仓/加仓单默认 **24小时（1天）有效**；`ttl=30m`、`ttl=1h`、`ttl=1d` 可覆盖，范围为整数1分钟至5天。市价单不能填写 `ttl`。有效期按每笔订单原始创建时间持久保存，重启、修改计划不会续期；升级前的旧挂单不追溯设置有效期。**程序端到期撤单依赖机器人运行和网络可用，停机或断网时可能延迟。**

助手跟踪的手动限价入场单（包括旧单）检测到部分成交后，会撤销未成交余量，以实际最终回执把已成交数量交给原生持仓及止损流程；极小的正成交量也会保留。撤单期间全部成交则按成交处理；回执不明时保留记录、提示核实，不提交替代订单。仅确认零成交结束时才清理对应空单和计划。记账中断会持久保存待处理状态，恢复或重启后继续核对。

订单查询和撤单回执会保留已观察的累计成交量。后续回执若成交量倒退或字段矛盾，助手与原生订单处理都会暂缓该订单，保留记录并等待一致回执，不会把已知成交误清理为零成交。此校验只作用于助手跟踪的手动限价入场订单。

已有同方向仓位时，重复开仓命令表示明确加仓；沿用原杠杆，存在挂单时先等待或撤单。同币种反方向请求会拒绝。加仓命令中明确提供的 SL/TP 会更新当前计划；未提供的继续沿用。没有多档入场、到价补仓或指标驱动加仓。

实盘开仓和加仓前，会重新查询交易所该币种仓位。本地没有记录却存在真实仓位、方向/数量不符、合约单位异常或查询失败时，拒绝提交，并保留计划和记录；不会自动接管、对冲或修正仓位。不同币种的外部持仓不影响该币种校验。模拟模式不查询真实账户；止盈、止损和平仓不受这项开仓校验阻塞。此检查不扫描外部挂单，也不能阻止核对后其他客户端同时改变仓位。

已成交仓位另有交易所止损确认：正常每30秒、待确认时每15秒重新读取原生跟踪的止损回执，核对活跃状态、方向、触发价、只减仓/整仓关闭标志和足额覆盖。成交后有15秒建单宽限，期间也不能加仓；持续未确认、恢复或实际保护变化时推送一次。每次加仓前强制重新核验，未确认则在修改计划和下单前拒绝，退出不受阻塞。模拟模式不会宣称交易所止损已确认。确认是查询时的快照，后续撤单、网络故障或原生重建止损仍可能造成保护空窗。

三个 TP：第一档退出初始数量的 30%，第二档退出当时剩余数量的 50%，第三档全部退出。两个 TP：第一档退出 50%，第二档全退。一个 TP：全部退出。**成交确认后**才推进阶段；部分成交、取消与重试不会提前跳档。最终止盈在仓位完全退出前一直有效。

分批 TP 和 `/close` 都会先检查合约数量、步长、适用的最小金额，以及 Freqtrade 对剩余仓位的门槛。合法的分批退出照常执行；本次减仓太小、取整为零或会留下无法继续处理的尾仓时，自动改为全平，并发送 TG 提示。Binance 线性合约只减仓订单享有的最小名义金额豁免会保留，不套用开仓金额门槛。

全平意图写入交易数据库，重启或价格回落后仍保留；确认部分成交且该订单结束后继续退出余量，期间拒绝加仓。整仓也不满足规则、提交失败或成交状态不明时，保留持仓和计划，暂停自动重复全平，发送提示并调用框架核验/尝试恢复交易所止损。止损恢复可能失败，请按提示核实交易所订单、仓位和止损后用 `/forceexit` 重试。只有确认平仓才清理计划，绝不会为了满足最小金额自动加仓。

TP1 成交后，保护位移至包含开平交易手续费的成本参考价；TP2 成交后移至 TP1。空头方向相反。手续费参考不包含未来滑点和资金费，因此不保证最终零损益。保护止损只收紧，修改计划或加仓不会自动放宽它。配置使用交易所止损；机器人本地同时判断保护价。`/setmanual` 是修改现有仓位计划，不会改变真实仓位方向。有未完成订单时不能改 TP，可以单独收紧 SL。所有 TG 交易变更都排入交易循环串行执行，避免与成交处理交错；超时且尚未执行的请求会取消，执行中的请求则提示先核实状态。

`/close <ID> [百分比]` 支持部分平仓，省略比例则全平；`/forceexit <ID|all>` 使用官方强制平仓流程。`/stopentry` 暂停新开仓，已有仓位继续管理；`/stop` 是停止交易处理。

## 每小时市场监控

每次分别发送 **BTC、ETH、SOL 三份消息**，每份合并：

- **1d、4h：** EMA20/EMA50 走势，以及最近 60 根已收盘 K 线的支撑/阻力参考。
- **1h、15m：** 当前走势与节奏，只参与走势判断，不产生入场、SL 或 TP 点位。
- **走势分区：** 顺势、回调、反弹、整理或大周期分歧。

所有分析排除未收盘 K 线。点位来自已确认局部高低点，缺少局部拐点时参考历史区间边界；不是预测目标，也不会写入交易计划或触发订单。每小时 UTC 整点后由后台任务取公共行情，机器人启动时也发送首轮报告。`/monitor` 可手动请求同样三份报告。网络错误逐币种、逐周期隔离，异常周期标记不可用。

## 收盘确认异动提醒

BTC、ETH、SOL 另有每分钟后台检查，只判断**最新已收盘 15m K 线**：

- **放量：** 本根成交量至少为此前 20 根均量的 2 倍，均量不含本根。
- **突破／跌破：** 相邻两根收盘价穿过同一 4h、日线阻力／支撑。参考位仅使用本根 15m 开始前已收盘的大周期数据，影线穿越不算。

同币种同一根 K 线的多个异动合并为一条消息，列出关键位、收盘价、涨跌幅与量比；同币种同类型冷却 60 分钟，换点位也不会绕过冷却，冷却内事件不补发。正常情况下在收盘后约一分钟内检测，网络或数据故障可能延迟。

去重和冷却状态单独保存在 `deploy/market_alert_state.json`，不读取或修改交易计划。进程启动先建立当前基线，从之后的新收盘 K 线开始判断；重启不批量补发历史，行情恢复只判断最新一根。状态先落盘再交给 TG 推送，因此重启不会重复提醒，但进程崩溃或 TG 发送失败可能丢失通知，不承诺必达。小时报告和手动 `/monitor` 保留，异动提醒不下单。参考周期缺失时会标注不可用，仍可提示放量及健康周期的穿越；成交量异常时仍可提示有效价格穿越。

## 运行

生产配置为 `deploy/config.json`，手动计划为 `deploy/strategy_state.json`。该目录不纳入 git。原配置中的交易所和 Telegram 凭据保留；不再加载 `.env` 中的 AI、数据库或旧回测参数。

```bash
python3 tools/prepare_watchdog.py
docker compose build
docker compose up -d
docker compose logs -f
```

准备工具只把 TG token/chat_id/topic_id 写入忽略提交的 `deploy/watchdog.json`（权限 0600），并创建健康和守护状态目录；不输出凭据。TG 配置变更后重新执行准备工具并重启 watchdog。

## 独立心跳守护

`watchdog` 是同机独立容器，每 30 秒检查一次。交易进程的轻量发布线程每 15 秒记录原生最后完成交易循环的时间、状态和快照时间；发布线程仍运行而交易循环卡住时，也会被识别。

首次启动宽限 180 秒，之后 `RUNNING`/`PAUSED` 的交易循环或快照超过 180 秒未更新、数据缺失/无效都会告警；重复重启机器人不会延长守护宽限。`/stop` 提醒交易处理已停止，`/pause` 的已有仓位管理正常时不告警。Binance 现货元数据与 USDT 合约公共接口连续两次不可达也会通知；公共接口正常不代表账户交易权限正常。

状态变化才通知，持续同一异常不会刷屏，恢复通知一次。TG 失败保留待通知状态；恢复后合并一条摘要，不逐条补发历史。通知尽力送达，超时无法保证绝不重复。守护状态文件损坏或无法写入时，以内存继续检查和去重，并明确通知持久化异常；存储恢复后补存状态，降级期间重启可能重复通知。守护只挂载 TG 专用配置、只读健康目录和自己的状态目录，读取不到交易所密钥、交易数据库、计划或 Docker socket；不自动重启、撤单或交易。整台主机断电或断网时，同机守护无法及时发出 TG 通知。

健康文件是 `user_data/health/assistant.json`，守护状态是 `user_data/watchdog/watchdog.json`，均不提交。`docker compose logs watchdog` 可查看不含凭据的守护状态。单独重启交易进程可用 `docker compose restart freqtrade`，守护继续运行。

上述 `up` 会按 `deploy/config.json` 的 `dry_run` 值运行；需要模拟时先设为 `true`。数据使用新的 `user_data/assistant_trades.sqlite`。HTTP API 已关闭，不映射端口；开仓和加仓只走 TG。`deploy` 使用目录挂载，使计划文件可以原子更新。

旧 `.venv` 不会自动升级或应用 TG 扩展；以 Docker 镜像为运行入口。需要本地依赖时，Python 3.12+，按 `requirements.txt` 安装。
